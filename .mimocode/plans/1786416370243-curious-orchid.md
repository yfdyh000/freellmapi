# FreeLLMAPI 迁移 Tauri 2 计划

> 日期:2026-08-11。基于 `my/框架迁移评估` 分支的评估文档、`poc/electrobun` 分支的 Electrobun PoC 实测、Tauri 2 官方文档核实,以及本机体积实测。
> 结论先行:**迁移可行且是当前最优路径**——Electron 壳层薄、`server-host.ts` 已框架无关、server 无 Electron 依赖;Tauri 2 壳 + Node sidecar 安装包实测压缩后约 **28–34MB**,解压后 C 盘占用约 **95–105MB**,两者均约为 Electron 的一半,且体积可继续演进。

## 1. 用户确认的约束

1. **用单独分支**开发,现 Electron 版本(`desktop/`)保持可发布,不阻塞现有用户。
2. **可接受写少量 Rust**(仅壳层:窗口/托盘/生命周期;业务代码仍 TS/Node)。
3. **Node sidecar 非强制**——在体积与开发成本间权衡,sidecar 打包方式先选开发成本低的,体积可逐步演进优化。
4. **体积约束分两个维度,都要核算**:
   - 安装包体积(下载/更新流量):挑战 <30MB,渐进式达成,非 P0 硬 gate;
   - **解压后 C 盘占用(安装后实际写入磁盘,即压缩前大小)**:尽量小——压缩只影响运输,运行时本体(node.exe ~88.5MB)解压后是物理占用,这是用户最在意的维度,决定 sidecar 打包方式选型。
5. Windows 优先,架构上兼容 mac/linux。
6. 实施阶段可用 agent(actor)并行推进(如 P0 两种打包方式并行实测、探索任务委托)。

## 2. 关键事实(已核实)

| 项 | 结论 |
|---|---|

## 3. 架构设计

**进程模型**:Tauri 主进程(Rust 壳)spawn Node sidecar(server-host.ts 打包)→ dashboard 窗口继续 `loadURL(http://127.0.0.1:<port>)`。现有"窗口=浏览器视图、数据走 HTTP"架构原样保留。

**渲染引擎:不捆绑 Chromium,用系统 WebView**。Windows=WebView2(Edge/Chromium 内核,Win10 1809+/Win11 系统自带,旧系统可带 bootstrapper)、macOS=WKWebView(Safari)、Linux=WebKitGTK 4.1。React 前端照常渲染;代价是引擎版本随系统浮动,前端以现代 Web 标准为主(React 19 + Tailwind),兼容风险低,但三平台需 UI 回归清单。

**跨平台**:Tauri 2 官方支持 Windows/macOS/Linux(+移动端可选);sidecar 用 SEA 按平台构建,`externalBin` 的 target-triple 命名天然支持三平台(如 `freellmapi-sidecar-x86_64-pc-windows-msvc.exe` / `-aarch64-apple-darwin` / `-x86_64-unknown-linux-gnu`);macOS 的 SEA 官方仅 arm64 CI 测试(Intel 需自测);Linux 需系统 webkit2gtk-4.1 等运行库。

- **端口**:沿用 31415 + `listenWithScan`(server-host.ts:64);SEA 启动后把实际端口写 stdout,Rust 读取后广播 `freeapi:ready`。
- **数据目录**:**独立目录 `<appData>\FreeLLMAPI_Tauri`**(2026-08-11 用户指示,参考 bun 分支 `FreeLLMAPI_Bun` 的做法)——Tauri 版调试/开发期**不共享 Electron 版数据**,防污染、防回退困难;dbPath/clientDist 以命令行参数传入 sidecar(壳显式传 `--db`,sidecar 默认值也是独立目录);后续需要时再做迁移工具。
- **生命周期**:Rust `setup` 时 spawn sidecar,退出钩子 kill 子进程 + 端口守护;**LAN 切换从"整 app relaunch"降级为"仅重启 sidecar"**(进程模型红利)。
- **单实例**:`tauri-plugin-single-instance`,回调打开 dashboard。
- **token/version 注入**:废弃 Electron preload `additionalArguments`,改 Rust 命令 `get_bootstrap()` 返回 token+version,renderer 在页面脚本前 await。

## 3.5 概念澄清:sidecar ≠ SEA(架构 vs 工艺)

- **sidecar 是 Tauri 的机制**:Tauri 应用 = Rust 壳 + 一到多个外部可执行文件(sidecar),壳启动时把它作为独立子进程拉起。sidecar 可以是任何可执行程序。
- **SEA 是把 Node 应用打成单文件 exe 的工艺**(Node 官方特性:运行时+代码熔成一个 exe,目标机器无需装 Node)。
- **本项目的 sidecar 就是用 SEA 工艺做出来的 exe**:① Tauri 壳(Rust)② sidecar = SEA 单文件 exe(node 运行时 + server 代码)③ 资源(client/dist、原生模块放 exe 旁 node_modules/)。
- **真正并排对比的是 sidecar 的三种工艺**:SEA / @yao-pkg/pkg / 直接带完整 node.exe——三者解压后都 ≈95-105MB(都含完整 node 运行时),差异只在打包脚本与维护性;选 SEA 因官方维护、零第三方依赖。

## 4. Sidecar 打包方式 —— P0 实测结论(2026-08-11 已跑通)

**P0 实测结果(Windows,Node 24.19.0,本机)**:

| 方案 | 开发成本 | 安装包体积 | 解压后 C 盘占用 | 冒烟结果 |
|---|---|---|---|---|
| **Node SEA 单文件**(CJS bundle + `--experimental-sea-config` + postject) | 中(已打通脚本) | ~25MB | 97MB(exe 本体) | ✅ 完整跑通(HTTP 200,含 better-sqlite3) |
| **SEA + UPX 压缩** | 低(一条 upx 命令) | ~28–30MB | **23.7MB exe + ~8MB 资源 ≈ 32MB** | ✅ 跑通(无损,运行时自解压到内存) |
| 直接带完整 node.exe + bundle | 最低 | ~35MB | ~105MB | ✅(等价于 SEA 拆开) |
| @yao-pkg/pkg | 低 | ~25–28MB | ~95MB | 未测(npm 12 的 EALLOWGIT 拦截其 git 依赖链) |

**选定方案:SEA + UPX**。理由:
- 解压后占用 32MB 左右,约为 Electron(200MB+)的 1/6,**满足"最小的本地文件(解压后)"首要目标**;
- UPX 是无损自解压压缩,运行时行为零差异、**不破坏调试**(对比:裁剪 node 会让生产/开发行为不一致,用户明确视为调试风险,弃用);
- 单文件分发简单(exe + 少量资源)。

**技术要点(Node 24 SEA)**:
- **Node 24 的 SEA 只支持 CJS main**(`mainFormat` 是 Node 25.5+ 的 `--build-sea` 才支持);`--build-sea` 命令也是 25.5+ 才有;
- CJS bundle 中 `import.meta.url` 为空 → 用 esbuild `banner` 定义 `__seaMetaUrl` + `define: {'import.meta.url': '__seaMetaUrl'}` 修复(SEA 里 `__filename` = exe 路径,`createRequire` 因此从 exe 旁 `node_modules/` 解析 better-sqlite3);
- better-sqlite3 + bindings 完整复制到 exe 旁 `node_modules/`(SEA 内 require 只能加载 builtin,文件系统模块必须走 createRequire);
- 构建链:`bundle-sidecar.mjs`(esbuild CJS)→ `--experimental-sea-config`(blob)→ copy node.exe + postject 注入 → `upx` → 资源目录。

**UPX 压缩级别策略(2026-08-11 用户确认)**:UPX 有 `-1`(最快)~ `--best --lzma`(最优)档。**开发/非 CI 构建用低级别**(`-1` 或 `-7`,秒级完成,体积大些无所谓),**CI/发布用 `--best --lzma`**(实测 97MB → 23.65MB,24.4%)。`build-sidecar-sea.mjs` 增加 `--upx-level` 参数控制(默认开发 `-1`,CI 显式传 `--best --lzma`;`--no-upx` 完全跳过)。

**遗留风险**:UPX 压缩可能触发杀软误报(需实测 Windows Defender);可接受的代价(安装包有签名可缓解)。裁剪 node(ICU/inspector)因调试风险弃用,除非未来体积硬缺口。

## 7.5 构建加速策略(2026-08-12 用户痛点:构建慢至系统卡死,期望 ≤5 分钟)

**根因(已实测确认)**:①机器 i5-2500S(2011,4 核)+ target 在 W 盘 HDD → 全量编译 400 crates 需 30-60 分钟且 4 核占满卡死;②**Cargo.toml profile 变更(如加 `[profile.dev] debug=false`)会使全部依赖指纹失效 → 触发全量重编**(本次卡死即因此);③profile 稳定时增量编译 ≤2 分钟,是快路径。**规则:profile/依赖变更 = 全量重编,避免频繁改动;改完保持稳定。**

**方案组合(按投入产出排序)**:
1. **CI 预构建 target 缓存(治本,即"预编译二进制")**:新增 workflow(.github/workflows/tauri-target-cache.yml)在 windows-latest(现代 CPU)跑 `cargo build --manifest-path desktop/src-tauri/Cargo.toml`,把 target/ 压缩上传 artifact;本地下载解压到 src-tauri/target → 本地永远增量编译(≤2 分钟)。换机/清缓存/全量重编场景不再本地硬扛。**注意:本地与 CI 的 rustc 版本须一致(1.97.1),否则缓存作废。**
2. **sccache(高 ROI 补充)**:本地/CI 共用缓存,跨构建复用编译产物;首次填充仍全量,但之后"重建"免全量。CI 侧 `mozilla/sccache-action` 自动缓存。
3. **cargo-binstall(仅工具链)**:CI 里快速装 tauri-cli/cargo 工具,不加速应用编译;本地已用 npm 版 @tauri-apps/cli 无此需求。
4. **release-fast profile(暂缓)**:opt-level=1 无 LTO 的开发用 release;改动 profile 会再触发全量重编,须与全量重编窗口合并执行,不在开发中途改。

**执行纪律**:①本地全量重编(任何原因触发)一律 `cargo build -j 2` 限流后台跑(CPU 降到 ~50%,不卡死),不占满;②profile/Cargo.toml 改动集中在"已知要全量重编"的时机;③日常改壳代码走增量(≤2 分钟)。

**CI 预构建实施方案(2026-08-12 用户选定,不再本地全量)**:
1. **钉 Rust 版本**:`desktop/src-tauri/rust-toolchain.toml` 写 `[toolchain] channel = "1.97.1"`(本地与 CI 指纹一致;本地 rustc 已是 1.97.1,加该文件不触发重编)。
2. **新 workflow** `.github/workflows/tauri-target-cache.yml`:
   - 触发:`workflow_dispatch`(手动)+ push 到 `my/tauri`(paths: `desktop/src-tauri/**`)
   - runner:`windows-latest`
   - 步骤:checkout → `dtolnay/rust-toolchain@1.97.1`(或依赖 rust-toolchain.toml 自动)→ `cargo build --manifest-path desktop/src-tauri/Cargo.toml`(debug)→ `tar -czf target.tar.gz -C desktop/src-tauri/target .` → `actions/upload-artifact`(tauri-target-win,retention 30d)
   - **注意**:CI 只编译 Rust 壳(不跑 build-sidecar-sea.mjs;sidecar 构建仍本地/发布时跑)
3. **远端(2026-08-12 用户指定)**:workflow 与分支推到 **YF-my 私有仓库**(隐私:构建产物/缓存不进公开仓库);本地开发仍用 my/tauri 分支,推送目标 = YF-my 的对应分支。
4. **本地消费**:下载 artifact → 解压到 `desktop/src-tauri/target/` → `cargo build` 增量(≤2 分钟)。换机/清缓存时重复此流程。
5. **验证**:下载缓存后改一行 lib.rs → 增量编译计时;再验证 READY 修复(dashboard 弹出)。

- **P1/P2**:现有 `desktop/src/__tests__/window-chrome.test.ts` 逻辑转 Rust 单测或删除;popover 快照对比 Electron 版字段一致性。
- **P3**:tag 触发 release,tauri-action 生成 latest.json,装旧版升级新版验证。
- **端到端**:LAN 开关、开机自启、复制 URL/Key、托盘 Quit、二次启动单实例,逐项手工回归(对比现 Electron 行为)。

## 9. 风险清单

1. **undici 深层行为**:`Symbol.for('undici.globalDispatcher.1')` 定制 + SOCKS 手写层,在 pkg/SEA 内 Node 版本锁死(v24),P0 冒烟必须覆盖。
2. **better-sqlite3**:ABI 匹配官方 node 二进制;SEA 走 assets+dlopen,需 P0 验证迁移 roundtrip(可复用 Electrobun PoC 已验证的 bun-sqlite roundtrip 思路)。
3. **解压后占用下不来**:node 运行时 88.5MB 是物理下限,裁剪 ICU 依赖自定义 base binary(pkg 需 `--public` 重建、SEA 需自编译裁剪版 node),若裁剪链不稳,解压占用将停留在 ~100MB(仍为 Electron 一半,可接受但达不到"尽量小")。
4. **WebView2 渲染一致性**:系统 Edge 版本不可控;client 玻璃效果在 Windows 本就是 CSS 模拟,风险低,需 UI 回归清单。
5. **macOS vibrancy**:Electron 原生 vibrancy → Tauri 需 `window-vibrancy` crate(风险中,备选实色底)。
6. **sidecar 残留/端口占**:主进程崩溃后 sidecar 存活;pid 文件 + 端口探测双保险。
7. **shell 插件安全**:capabilities 用精确 args 白名单(严禁 `args:true`),sidecar 固定文件名。
8. **updater 强制签名**:与现有 electron-builder 的 latest*.yml 不兼容,必须新增签名密钥链路。
